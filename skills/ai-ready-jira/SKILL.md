# AI-Ready Jira

Get a UW ticket into shape for the Claude Code flow. `/plan` researches and plans **from the
ticket**; if the ticket is vague, it plans for a guessed intent — the exact failure the
Confluence process warns against. This skill fixes that at the ticket by interviewing the
person who filed or owns it and rewriting it to have three things:

1. **Correct scope** — which product(s) and platform(s), and what's out of scope.
2. **A clear, text description of the issue** — meaning stated in words, not trapped in a
   screenshot.
3. **Real reproduction steps** — for bugs.

The description shape lives in `references/ticket-template.md` — **read it** before rewriting.

## What this skill does NOT do

It does **not** invent or write the "AI Implementation Contract." That machine-readable JSON
block is generated by the repo's `/create-jira-ticket` command and parsed by `/plan` and
`/raise-pr`; its schema lives with those commands, and this skill has no access to it.
Fabricating a JSON shape would produce output those commands can't parse — worse than
nothing. A well-scoped, clearly-described ticket is precisely the input `/create-jira-ticket`
and `/plan` need; producing that is this skill's entire job. Do not guess field names, do not
reverse-engineer a schema, do not output a JSON contract.

## The one principle

You are not the author of these tickets, you cannot see the codebase, and **you often cannot
reliably interpret the screenshots** on a ticket. So the job is **elicitation, then faithful
restructuring** — never invention. When the ticket and the user's answers don't determine
something, record it as an open question for the team; never fill it with a plausible guess.

## Prerequisites

Atlassian tools must be available. Tickets are in the `UW` project on `fanduel.atlassian.net`
(use that as `cloudId`; if rejected once, call `getAccessibleAtlassianResources` for the
UUID). If the tools aren't available, say so — don't fabricate ticket contents.

## Workflow

### Step 0 — Scope which ticket(s)
A specific key → that ticket. A filter ("the P3s", "everything In Analysis") → read the
board, confirm the shortlist with the user first. "Which are ready?" → read-only audit, don't
rewrite. Do **not** rewrite Epics — offer to prep their children instead.

### Step 1 — Read the ticket fully
Pull summary, description, **comments** (for a Defect the cause is often half-diagnosed
there), **issue links** (linked PRs, a twin in the other product), and the **attachment
list**. Note every screenshot referenced in the description.

### Step 2 — Find the gaps
Decide the work type from the issue type. Then identify what's missing for that type against
the Definition of Ready. Typical gaps:
- Scope not explicit (product implied by a `[TVG]` prefix but platform unstated; multi-product
  not confirmed).
- Issue described only by a screenshot, with no text saying what's wrong.
- **Screenshots you can't interpret** — you cannot reliably read what a UI screenshot depicts.
  Any screenshot whose meaning isn't already stated in text is a gap to ask about, NOT
  something to describe yourself from the image.
- For a Defect: no reproduction steps, no expected-vs-actual, no consistency/where-seen.
- Visual work with no specific Figma node.

If the ticket already meets the Definition of Ready, say so and skip it.

### Step 3 — Interview the user (the core)
Ask **targeted** questions for the gaps found — not a generic questionnaire. Use the
`ask_user_input_v0` tool for anything with discrete choices (product, platforms, consistency,
who-can-reproduce) — tapping beats typing. Use plain free-text
questions (in prose) for things that need the user's own words: **describing each image**,
stating expected-vs-actual, giving repro steps.

**Images — ask the user to describe EVERY image, one question per image.** The user running
this skill has UW access and can see the attachments; you cannot reliably read a UI
screenshot. So for **each** image on the ticket (every attachment and every image embedded in
the description), ask a separate question: what does this image show, and what should the
reader look at? Reference the image by its filename or its position/label in the description
so the user knows which one you mean (e.g. "image-20260128-224925.png (labelled 'TVG')").
Put the user's answer verbatim-in-spirit into the description as that image's caption and into
the issue description. **Never** write a caption from your own guess at an image, and never
skip an image because you think you can infer it.

**Mobile platforms — never assume a mobile bug is isolated to one platform.** TVG and FDR each
run on multiple mobile platforms (Mobile Web, native iOS/Android, RN). A bug reported on one
mobile platform (e.g. "TVG Mobile Web") **cannot be assumed** to be exclusive to it — the same
root cause often affects the others. So when a Defect is reported on a mobile platform:
  - Record the platform(s) the user has actually confirmed.
  - Do **not** mark the other mobile platform(s) as out-of-scope on the user's say-so alone.
  - Add an explicit **first task for the developer** who picks up the ticket: attempt to
    reproduce the issue on the other mobile platform(s) for that product, and expand the scope
    if it reproduces there too. This goes into the rewritten description (see Step 4) so it
    travels with the ticket.

Question bank (pull only what's missing):
- **Scope (all):** which product(s)? which platform(s) per product? anything explicitly out
  of scope? multi-product → confirm it stays one ticket (it's always a small change)?
- **Defect:** what does the user see vs. what should they see (in words)? exact steps to
  reproduce? always or intermittent (or only with specific data)? where seen (product +
  platform + device/browser)? who can reproduce (you / agent / needs device)? any linked PR
  or half-diagnosis in comments? does the area look like a shared component? — but do NOT ask
  them to commit a cause or a fix; the cause is left for `/debug`.
- **Story/Task:** are the acceptance criteria complete and checkable? behind a flag — on/off
  behaviour?
- **Visual:** the specific Figma node + target breakpoints?
- **Spike:** the single question + timebox (deliverable is findings, not a PR).
- **Finding:** confirm provenance + affected assets are captured faithfully.

Never ask for code specifics (file paths, flag-hook return shapes) — those are `/plan`'s job
against the real repo. Ask about intent, scope, and what the user can see.

### Step 4 — Draft Acceptance Criteria (Gherkin) and get the user's sign-off
Every ticket the skill preps gets **Acceptance Criteria that define "done"**, written in the
**Gherkin** pattern so they're unambiguous and testable:

```
Scenario: <short name>
  Given <starting context>
  When <action>
  Then <observable, checkable outcome>
```

- **Suggest** the ACs — derive them from the confirmed scope, the issue description, and the
  reproduction steps (for a Defect, the fix's ACs are essentially "the reproduction no longer
  produces the bug, and nothing adjacent regressed"). Cover the happy path plus the relevant
  edge/negative cases and, for visual work, the target platform(s)/breakpoint(s).
- **Include the mobile-reproduction task as an AC when it applies**, e.g. a scenario asserting
  the behaviour holds on the other mobile platform(s) once reproduction is confirmed.
- If a flag is involved, write scenarios for both on and off.
- **Show the suggested ACs to the user and let them edit/approve** — these are suggestions to
  validate completion, not fabricated certainties. Don't invent an AC for behaviour nobody
  confirmed; if something is unknown, ask or leave it as an open question.

**Where the ACs go:** put them in an `## Acceptance Criteria` section **in the ticket
description**. Do not write them to a custom Acceptance Criteria field — the description is the
single place the ACs live.

### Step 5 — Draft the rewritten description
Following `references/ticket-template.md`: opening context (no heading — it's the top of the
description), then the work-type sections. For a Defect that means a **text** issue
description, **numbered reproduction steps**, **each image captioned in the user's words**, and
— when the bug is on a mobile platform — the **explicit "developer: reproduce on the other
mobile platform(s)" task**. Keep all original images, links, and reporter context —
restructure, don't discard. Set the summary to `[PRODUCT] <specific outcome>` if it isn't
already.

### Step 6 — Confirm, then update Jira
**Always show the user the proposed new summary, description, Acceptance Criteria, and label
changes before writing.** On approval:
1. Fetch and preserve all current attachments from the ticket (download links or note them).
2. Update via `editJiraIssue` (`contentFormat: "markdown"` for the description — the ACs are 
   an `## Acceptance Criteria` section within it). Keep existing labels and add the product 
   label. **Important:** the attachment array should be preserved during the update to prevent 
   Jira from deleting attachments when the description is updated.
3. If any attachments were referenced in the old description with broken URLs, add a proper
   reference or note in the "Known context" section instead (e.g. "Video evidence: 
   isthisintended_.mov demonstrates the issue").

Don't change status/priority/assignee unless asked. Then report what changed and any open
questions still owned by the team. If the ticket is now clear, you can mention that running
`/create-jira-ticket` in the repo is the next step if the team wants the Implementation
Contract generated — but this skill does not generate it.

## Guardrails
- **Preserve all attachments** — Before editing the ticket description, download and store
  copies of all attachments (images, videos, PDFs, etc.). When updating the ticket via
  `editJiraIssue`, pass the attachments array back unchanged to prevent loss. Updating the
  description should NEVER cause attachments to be deleted. If attachments are referenced
  in the old description with broken blob URLs, fix the reference format but keep the
  attachment itself (do not rely on the blob reference).
- **Elicit, don't invent** — especially for images. Ask about EVERY image, one question each;
  never caption from your own guess.
- **Never assume a mobile bug is isolated to one platform** — add the developer's
  "reproduce on the other mobile platform(s)" task, and don't out-scope the others on the
  user's say-so alone.
- **Always add Acceptance Criteria in Gherkin** (Given/When/Then), suggested from confirmed
  scope + description + repro, and approved by the user; put them in an `## Acceptance
  Criteria` section in the description (not a custom field).
- **No fabricated JSON contract**, no guessed schema, no reverse-engineering.
- **Never pre-write a Defect's cause or fix** — capture symptom, repro, and shared-component
  risk; leave the cause for `/debug`.
- **Product is mandatory** — the engineer can't pick the codebase without it.
- **Don't rewrite Epics.**
- **Confirm before every write.**

## Example (shape, not script)
**User:** "Get UW-1234 ready for Claude Code."
1. Read it: `[TVG]`-prefixed Defect, description is a couple of lines plus two images
   (attachments + embedded), no repro steps, `Frontend` label only.
2. Gaps: platform unstated; the "what's actually wrong" is only shown in images; no repro;
   two images I can't interpret; no Acceptance Criteria.
3. Interview: `ask_user_input_v0` for product/platform confirm + consistency + who-reproduces;
   one free-text question **per image** ("describe image-…-224925.png (TVG)"; "describe
   image-…-224939.png (FDR)"); free-text for expected-vs-actual. Because it's a mobile bug,
   plan to add the "reproduce on the other mobile platform(s)" developer task.
4. Suggest Gherkin ACs (happy path + the mobile-reproduction scenario + no-regression),
   show them to the user, take edits.
5. Draft: opening context (product + confirmed platform + mobile-uncertainty task), issue
   description in the user's words, numbered repro steps, images with the user's captions.
6. Show summary + description (with the `## Acceptance Criteria` section) + labels; on approval
   `editJiraIssue` + add `TVG` label; report, and note
   `/create-jira-ticket` as the next step if they want the contract.
